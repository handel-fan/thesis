The four I meant were:

**12. Counterexample-guided numerical lowering**
**15. Error-directed fusion**
**16. Numerically aware tiling**
**19. Joint numerical optimization across multiple IR levels**

And the first thing to make precise is that I did **not** establish “nothing related to these exists anywhere.” What I established was narrower:

> I deliberately searched for the actual mechanism we proposed, found substantial neighboring work, but did not find a paper/system doing that exact thing.

That is enough to keep investigating them. It is not enough to write “this is novel” in a proposal.

Here is what each idea actually means, from the beginning, and how I got to that conclusion.

---

# 12. Counterexample-guided numerical lowering

## What is the idea?

A compiler often has several ways to implement the same high-level operation.

Suppose the original program contains:

```text
matrix multiply
```

and the compiler could lower it in several ways:

```text
Lowering A:
FP32 multiply + FP32 accumulation

Lowering B:
FP16 multiply + FP32 accumulation

Lowering C:
FP16 multiply + FP16 accumulation
```

Assume the requirement is:

$$
\text{final numerical error} \leq 10^{-4}
$$

The usual way to choose would be something like:

1. estimate the error of A;
2. estimate the error of B;
3. estimate the error of C;
4. choose the fastest one satisfying the bound.

**Counterexample-guided lowering is a different strategy.**

The compiler starts aggressively:

```text
Try C.
```

Then some verifier asks:

> Is C guaranteed to stay within \(10^{-4}\) error for every allowed input?

Suppose the answer is no.

Crucially, the verifier doesn't merely say:

```text
FAILED
```

It gives you an input demonstrating the problem:

```text
A = ...
B = ...

this lowering produces error = 0.0021
```

That input is the **counterexample**.

Now the compiler learns something from it.

Maybe it discovers:

```text
FP16 accumulation cannot be used for this reduction.
```

So the next proposal might be:

```text
FP16 multiply
FP32 accumulation
```

Check again.

If another counterexample appears, refine again.

So the algorithm looks like:

```text
propose implementation
        ↓
check numerical guarantee
        ↓
      passes? ───── yes → finished
        |
        no
        ↓
obtain counterexample
        ↓
refine implementation search
        ↓
try again
```

The research contribution would be the **refinement algorithm**:

> Given a numerical counterexample, how do you infer which lowering decision must change without simply falling back to FP64 everywhere?

That is the interesting part.

---

## Why did I think this might not already exist?

I specifically searched around the mechanism, not just the words “numerical compiler.”

The searches were along the lines of:

```text
CEGIS floating point lowering
counterexample guided mixed precision
counterexample guided floating point optimization
counterexample guided numerical compiler transformation
counterexample guided precision tuning
```

I **did find counterexample-guided floating-point research**.

One concrete hit was work on **counterexample-guided floating-point loop invariant synthesis**.

That uses the general pattern:

```text
guess something
check it
get counterexample
refine guess
```

for proving floating-point properties.

So I could not claim:

> “Nobody has ever used counterexamples for floating-point reasoning.”

That would be false.

What I did **not** find was this:

> The thing being synthesized is a **compiler lowering**, and numerical counterexamples are used to refine the choice of lowering transformations until an accuracy contract is satisfied.

In other words, I found:

```text
CEGIS + floating point
```

but not:

```text
CEGIS
+
search over compiler lowering decisions
+
explicit numerical error contract
```

That's why this survived.

### What could still kill it?

Someone may call the same idea something other than “counterexample-guided lowering.”

For example:

* refinement-based numerical optimization,
* verification-guided precision tuning,
* solver-guided implementation selection,
* CEGIS approximate compilation.

So this one needs a deeper literature chase before trusting it.

But among the twenty, it was one of the few where my targeted searches didn't immediately cough up the proposed algorithm.

# 15. Error-directed fusion

## First: what is fusion?

Suppose the program says:

```text
x = A * B
y = x + C
```

A compiler could execute these separately:

```text
compute A * B
store x

load x
compute x + C
store y
```

Or it could **fuse** them:

```text
compute A * B
immediately add C
store y
```

Fusion is extremely common in tensor/GPU compilation because it can avoid intermediate memory traffic.

Normally the compiler asks questions like:

> Will fusion make this faster?

> Will it reduce memory traffic?

> Will it hurt parallelism?

---

## What is the proposed new idea?

Make **numerical accuracy** part of the fusion decision.

Why would fusion affect the numerical result?

Because changing the implementation can change things such as:

* where values get rounded;
* whether intermediate values are stored in FP16 or FP32;
* whether an FMA instruction gets used;
* accumulation order;
* whether an intermediate is converted between formats.

So two implementations that represent the “same mathematics” can behave differently numerically.

The proposed compiler decision becomes:

```text
Candidate fusion:

operation A
operation B

       ↓ fuse?

performance improvement = 1.4x
additional numerical error <= 3e-5

remaining allowed error = 5e-5

Therefore fusion is allowed.
```

But perhaps another fusion gives:

```text
additional error <= 8e-5
```

and therefore gets rejected.

So the proposed method is:

> **Predict or bound how fusion affects the final numerical error and use that bound when deciding whether to fuse.**

Not:

> “Analyze whether fusion changes floating-point answers.”

We already know it can.

The actual compiler algorithm is:

$$
\text{fusion decision}
=
f(\text{performance},\text{memory},\text{numerical error budget})
$$

---

## How did I look for this?

I searched things like:

```text
floating point fusion numerical error compiler
error aware fusion compiler
accuracy aware operator fusion
numerically stable fusion compiler
fusion error bound tensor compiler
FMA contraction numerical error optimization
```

What I found was **lots of surrounding evidence**.

There is substantial existing work/documentation showing that:

* contraction into FMA changes floating-point behavior;
* operation ordering matters;
* fused GPU/tensor implementations can change accumulation behavior;
* compiler transformations can change numerical results.

So the **phenomenon** is absolutely known.

I also found current NVIDIA documentation explicitly warning that compiler transformations and accumulation ordering can change numerical results.

But I did **not** find a fusion optimizer whose decision rule is essentially:

```text
for each candidate fusion:
    derive error effect
    compare with global accuracy constraint
    decide whether fusion is legal/profitable
```

That's the missing mechanism.

And that's why I did **not** conclude:

> “Numerical effects of fusion are new.”

They're clearly not.

I concluded:

> **I couldn't find an explicit-error-budget-driven fusion-selection algorithm.**

That is much narrower.

### Why this one interests me

It is much harder for someone to dismiss as:

> “You put an error annotation in MLIR.”

Because the actual thing you're inventing would have to be something like:

> Given two possible fused/unfused implementations, derive or estimate their differential contribution to an end-to-end error constraint and incorporate that into fusion profitability.

There has to be a real analysis.

---

# 16. Numerically aware tiling

This one needs an introduction because **tiling sounds completely unrelated to accuracy at first**.

## What is tiling?

Say you're multiplying huge matrices.

Instead of computing the whole thing in one enormous loop:

```text
for every row
    for every column
        for every k
            ...
```

the compiler divides the matrices into little blocks:

```text
16 × 16 tiles
```

or:

```text
32 × 32 tiles
```

etc.

Then it operates on those blocks.

This is usually done for hardware reasons:

* cache;
* vector units;
* GPUs;
* Tensor Cores;
* register usage;
* parallelism.

So normally the compiler chooses tile size by asking:

> Which tile dimensions make this machine fastest?

---

## Why would tile size affect numerical error?

Suppose you're computing:

$$
a_1b_1+a_2b_2+\cdots+a_nb_n.
$$

Floating-point addition isn't perfectly associative.

So:

$$
((x_1+x_2)+x_3)+x_4
$$

can produce a slightly different answer from:

$$
(x_1+x_2)+(x_3+x_4).
$$

Different tilings can cause partial sums to be grouped differently.

For example:

```text
Tile size 4:

sum first 4 values
sum next 4 values
combine partial sums
```

versus:

```text
Tile size 16:

sum 16 values using some hardware instruction
```

They can also cause the compiler to select different hardware.

For example, one tile configuration might permit a Tensor Core instruction with one particular input/accumulation precision, while another might result in a different sequence of operations.

So:

```text
tile shape
   ↓
hardware implementation
   ↓
accumulation structure
   ↓
rounding behavior
   ↓
numerical error
```

Now the thesis idea becomes:

> **Choose tile shape using both predicted execution cost and numerical error.**

Imagine:

```text
                 runtime       error

16×16              10 ms       2e-6
32×32               7 ms       8e-5
64×64               5 ms       3e-3
```

and the user requires:

$$
error\leq10^{-4}.
$$

The compiler chooses `32×32`.

Not because it's the most accurate.

Not because it's the fastest.

Because it's the fastest configuration satisfying the required accuracy.

---

## How did I search this?

I used combinations like:

```text
accuracy aware tiling floating point
error aware tile size compiler
numerical stability tile size matrix multiplication
roundoff tiling GEMM compiler
tile size accumulation order numerical error
```

And this produced an interesting result.

I found very clear evidence for the **premise**.

Current NVIDIA Tile IR documentation specifically discusses numerical stability and explains that changing tile size can alter:

* which MMA operations get selected;
* accumulation order;
* intermediate behavior;
* ultimately the floating-point result.

So this is not us inventing a fake connection:

```text
tiling → numerical behavior
```

The connection is real enough that NVIDIA documents it.

But I did **not** find:

> a compiler tile-size selector whose optimization problem explicitly includes an analytical/user-provided numerical-error constraint.

Most tile-selection work I found was about:

```text
runtime
throughput
occupancy
memory traffic
```

not:

```text
runtime subject to final error <= ε
```

That's why I marked this one as having no exact match.

### This one has a particularly clean thesis shape

The novelty would **not** be:

> Tiling affects rounding.

Known.

It would **not** be:

> MLIR can tile operations.

Very known.

It would be something like:

> **We introduce a cost model and selection procedure that jointly models the performance and numerical-error consequences of alternative tilings and chooses the fastest tiling satisfying an end-to-end error bound.**

Now there is something specific that could succeed or fail experimentally.

---

# 19. Joint optimization across multiple IR levels

This is probably the easiest one to accidentally describe as nonsense, so start with what the problem actually is.

## MLIR doesn't make every decision at once

Imagine the compiler starts with:

```text
matrix multiplication
```

At a high abstraction level, it might choose:

```text
algorithm A
```

versus:

```text
algorithm B
```

Later, after that decision has already been made, another compiler level chooses:

```text
tile size
```

Later:

```text
vectorization strategy
```

Later:

```text
FP16 versus FP32
```

So you can imagine:

```text
HIGH LEVEL

choose algorithm
      ↓

MID LEVEL

choose tiling/reduction structure
      ↓

LOW LEVEL

choose vectors / precision
```

Those decisions are typically represented at different points in the compiler.

---

## What's the numerical problem?

Suppose the high-level compiler makes what locally looks like the best choice:

```text
Algorithm A
```

Then later the low-level compiler discovers:

```text
Algorithm A requires FP32 to satisfy the error bound.
```

But perhaps another high-level choice:

```text
Algorithm B
```

would permit:

```text
FP16
```

and the total program would be much faster.

So:

```text
best high-level choice
+
best low-level choice
```

is not necessarily:

```text
best overall choice
```

because the choices interact.

Concrete imaginary table:

```text
High-level      Low-level      error       runtime

A               FP16           too high      4 ms
A               FP32           valid         9 ms

B               FP16           valid         6 ms
B               FP32           valid        11 ms
```

If you first decide:

```text
A is the best algorithm
```

and only later choose precision, you end up at:

```text
A + FP32 = 9 ms
```

But the global answer was:

```text
B + FP16 = 6 ms
```

So the idea is:

> **Don't let each abstraction level optimize independently. Search the interacting choices jointly under one numerical-error requirement.**

Mathematically, something like:

$$
\min_{H,M,L}
Cost(H,M,L)
$$

subject to:

$$
Error(H,M,L)\leq\epsilon
$$

where:

* \(H\) = high-level choice;
* \(M\) = middle-level choice;
* \(L\) = low-level choice.

---

## What did I look for?

I searched combinations like:

```text
multi level IR numerical optimization error bound
cross level floating point optimization compiler
hierarchical mixed precision compiler
multi level compiler numerical accuracy
high level low level jointly optimize numerical accuracy
MLIR cross level accuracy optimization
```

And here the interesting result was that **all the pieces exist nearby**.

I found work on multi-level IR optimization.

I found work specifically about preserving/raising abstraction levels in MLIR because different optimizations become possible at different levels.

I found numerical compilers like Herbie with multiple representations.

I found systems combining more than one numerical optimization technique.

And Poseidon gets particularly close because it combines numerical rewriting and precision tuning through one optimization system.

But what I did **not** find was:

```text
actual choices at multiple compiler abstraction levels
             +
joint search rather than sequential optimization
             +
single explicit end-to-end numerical constraint
```

That three-part combination.

And that's critical.

Because if somebody already does:

```text
rewrite + mixed precision
```

that's #6, which we found is already occupied.

For #19, the intended distinction is:

```text
Linalg-level transformation
        ↕
Vector-level transformation
        ↕
Arith-level precision choice
```

with the optimizer reasoning across those boundaries.

That is a different claim.

---

# Why these four survived when almost everything else died

Most of our original ideas were fundamentally about **numerical analysis itself**:

```text
choose precision
bound error
infer sensitivity
select approximations
find input preconditions
```

There are decades of numerical-program-analysis research doing that.

These four move the question toward:

> **How should numerical constraints alter compiler structural decisions?**

Specifically:

```text
12 → how do counterexamples alter lowering choices?

15 → how should accuracy alter fusion?

16 → how should accuracy alter tiling?

19 → how should accuracy couple decisions made at different IR levels?
```

That is why my searches had a different result.

I found mountains of surrounding work demonstrating that all the ingredients are real.

But for those four, I did not immediately find someone who had assembled the ingredients into the **specific compiler decision procedure we were describing**.

And among them, **#16 is probably the easiest one to explain cleanly to your professor**:

> Tiling is currently primarily selected for hardware performance. Tiling also changes floating-point accumulation behavior and sometimes the underlying hardware implementation. Develop a tile-selection algorithm that minimizes estimated runtime subject to an explicit numerical-error bound.

That statement has a very obvious:

```text
existing thing:
performance-driven tiling

new thing:
accuracy-constrained tiling-selection algorithm
```

Whether it's actually publishably novel still requires a deeper search, but at least the proposed contribution itself is no longer foggy.
