## 1. What worked today

A minimal POC compiled a Lean program containing a TensorLib matrix multiplication, intercepted an annotated function call in **early LCNF**, retrieved the called function's original Lean type from the declaration environment, associated its input and result types with the LCNF operands, and emitted textual **StableHLO**.

The essential input was:

```lean
structure TypedTensor (dims : List Nat) (dtype : Dtype) where
  raw : Tensor

@[ltom_poc, noinline]
def matmul2x2 (x : TypedTensor [2, 2] .float32)
    (y : TypedTensor [2, 2] .float32) : TypedTensor [2, 2] .float32 :=
  ⟨get! (Tensor.Ufunc.matmul x.raw y.raw)⟩
```

The LCNF pass found the call, and the compiler's environment exposed the complete declaration type. Its recorded association was:

```text
[POC] call=matmul2x2
[POC] operand0=x type=tensor<2x2xf32>
[POC] operand1=y type=tensor<2x2xf32>
[POC] result=_x.54 type=tensor<2x2xf32>
```

The generated file, `experiments/ltom_poc/artifacts/matmul.mlir`, contained:

```mlir
module {
  func.func @matmul(%x: tensor<2x2xf32>, %y: tensor<2x2xf32>) -> tensor<2x2xf32> {
    %z = stablehlo.dot %x, %y : (tensor<2x2xf32>, tensor<2x2xf32>) -> tensor<2x2xf32>
    return %z : tensor<2x2xf32>
  }
}
```

The script also executed the original TensorLib operation successfully (`TENSORLIB_OK`) and reported the generated MLIR file (`POC COMPLETE`). This is **emission of StableHLO text**, not execution of the generated StableHLO. The existing Lean computation was not replaced.

### How the POC works

1. `LtomPocSupport.lean` defines `TypedTensor`, registers the `@[ltom_poc]` tag, and installs a compiler pass after the initial LCNF pass (`PassInstaller.installAfter .base \`init`).
2. `Main.lean` declares an annotated, `noinline` matrix-multiplication wrapper and calls it. `noinline` keeps the recognizable call available to the experiment.
3. The custom pass traverses LCNF instructions, recognizes a call to a tagged function, and reads its original type with `getConstInfo fn`.
4. Helpers inspect the parameterized `TypedTensor` types, extract `[2, 2]` and `.float32`, and translate them into `tensor<2x2xf32>`.
5. The pass associates those extracted types with the actual two LCNF call operands and result binder, then constructs a `stablehlo.dot` function as text.

**Important architectural precision:** The POC does **not** change LCNF to carry those rich tensor types. It makes the relevant information available in **Lean's type/declaration environment**, which the LCNF pass can consult.

### Implementation issues resolved

- The thesis project initially used Lean **4.33.0**, while the TensorLib checkout targeted **4.35.0**. TensorLib failed under 4.33 because `Int.toFloat32` was unavailable. Upgrading the project's Lean toolchain allowed further compilation.
- A full `lake build TensorLib` then failed in an unrelated `TensorLib.LOrd` proof. The experiment required `TensorLib.Ufunc`, so it imported and built that narrower module successfully, without changing TensorLib's source.
- The type-extraction helper initially assumed numeric dimensions were represented by a direct numeral expression. The actual elaborated expression wrapped a numeric literal in `OfNat.ofNat`. The extractor was updated accordingly.
- Lean also required explicit constructors such as `Expr.lit (Literal.natVal n)` in the relevant patterns. After those fixes, the POC ran successfully.

These were implementation/debugging issues, not evidence that the underlying LCNF-plus-declaration-environment approach failed.

### Technical synthesis — not a quotation

TensorLib's ordinary tensor is conceptually:

```lean
structure Tensor where
  dtype : Dtype
  shape : Shape
  data : ByteArray
  -- other representation fields
```

The shape and dtype are **fields of a tensor value**, not parameters of its Lean type. Consequently, a signature such as `Tensor → Tensor → Err Tensor` does not specify the exact input or result shapes or element dtypes, even when a particular function body constructs tensors with literal dimensions and dtypes.

This is **not** a claim that compile-time information is intrinsically irrecoverable after elaboration. For some programs, inspecting construction sites and following dataflow would recover it. However, implementing such analysis across TensorLib operations, calls, and transformations could expand the thesis considerably. Some tensors also genuinely depend on runtime inputs (for example, external files), so a compiler cannot always assign exact static dimensions without additional restrictions or specialization.

`TypedTensor` moves the required information into a form the **existing** Lean compiler exposes conveniently:

```lean
TypedTensor [2, 2] .float32
```

This type is a parameterized type constructor applied to dimensions and dtype. Rather than recovering those properties from the program's computations, the POC reads them directly from the declared type. The design uses existing compiler facilities instead of modifying Lean's IR or implementing general tensor-shape analysis.

The intended term is **explicit static declaration**, not *compile-time inference*: the compiler is being told the properties rather than deducing them.

### Technical synthesis — not a quotation

The key distinction is between **information that can exist at compile time** and **information that this particular Lean compiler exposes at our chosen interception point without extra engineering**.

A compiler *could* be extended to preserve or recover tensor metadata from construction sites and value flow. That is not the route selected for the thesis POC. Instead, we impose a static interface, retrieve its declaration types through Lean's existing environment, and proceed to StableHLO lowering.

One correction to the wording in the quoted observation: the POC does **not** explicitly record the tensor properties *inside LCNF*. It records them in type declarations that remain accessible **from** the LCNF pass. The engineering point remains the same: use the available facilities to preserve and retrieve the information with minimum friction.

In short: **replace ambiguity with explicit compile-time type clarity, rather than build a general inference system.**

### Technical synthesis — not a quotation

A thesis compiler can legitimately accept a **restricted source language or usage contract**. It need not automatically convert every TensorLib constructor, JSON loader, or other tensor entry point. A practical contract is that functions selected for compilation use explicitly annotated tensor parameters and results, plus a documented subset of TensorLib operations and programming patterns.

For example, thesis examples may be required to use `TypedTensor` and annotated wrapper functions. Automated migration of TensorLib's complete codebase is not a prerequisite to demonstrating the translation.

This also means the experiment should be described as compilation of a **restricted, statically specified TensorLib subset**, not arbitrary unmodified TensorLib programs.

## 5. Drawbacks and limitations of the chosen approach

1. **Extra annotations and wrappers.** Source programs must conform to a thesis-specific interface. This creates some boilerplate and prevents claiming transparent compilation of arbitrary TensorLib code. This is an acceptable explicit prerequisite, not necessarily a problem to automate away.

2. **The current wrapper does not enforce truthfulness.** The definition

   ```lean
   structure TypedTensor (dims : List Nat) (dtype : Dtype) where
     raw : Tensor
   ```

   permits a raw tensor with shape `[3, 3]` and dtype `.float64` to be wrapped as `TypedTensor [2, 2] .float32`. Lean verifies that the *wrapper type* matches a signature, not that the runtime tensor's metadata matches its claimed parameters. For a sound compilation contract, the thesis must either validate shape/dtype when constructing or importing wrapped tensors, strengthen the wrapper with an invariant, or state the consistency requirement explicitly as an assumption.

3. **Static annotations must remain consistent through operations.** Marking entry-point tensors is not, by itself, sufficient for arbitrary tensor expressions. The compiler still needs rules for the supported operations' output shapes and dtypes (or explicit result annotations), plus an account of how those properties propagate through supported calls.

4. **Dynamic or externally determined shapes are restricted.** File/JSON inputs, runtime reshapes, or data-dependent dimensions may lack a single exact compile-time shape. The thesis can exclude these cases, require checks or shape-specialized entry points, or support them separately later. There is no need to solve them all now.

5. **Current code generation is narrow.** The POC recognizes an annotated matrix-multiplication wrapper and emits `stablehlo.dot`. It does not inspect or generally translate arbitrary TensorLib operations, conditional branches, loops, or compositions.

6. **Generated MLIR is not yet validated end-to-end.** The experiment emitted textual StableHLO and independently ran the original TensorLib function. It did **not** demonstrate successful StableHLO parsing/verification, execution of generated MLIR, or matching numerical results between the two execution paths.

7. **Restricting the source language limits generality.** This is a conscious tradeoff: stronger assumptions simplify the compiler, but the thesis must state precisely what programs it supports and avoid suggesting unrestricted TensorLib compatibility.

These limitations do **not** undermine the successful narrow result: the compiler can identify an early-LCNF call and recover statically declared tensor metadata from Lean's declaration environment.

## 6. Working conclusion and next technical milestones

**Decision:** Retain `TypedTensor` as an acceptable source-level prerequisite for the thesis prototype. Do not spend effort on wholesale TensorLib migration or automatic general-purpose shape/dtype inference unless later experiments establish that it is needed for the research goal.

The design principle established today is to **work with the existing Lean compiler's available information channels**, rather than extend the compiler merely to avoid explicit annotations.

The next meaningful steps are to verify the generated StableHLO with appropriate tools, support a small collection of tensor operations and their type/shape rules, define the accepted source subset, and decide how to enforce or assume the correspondence between `TypedTensor` annotations and the underlying runtime tensor.

**Result of the day:** A successful proof that *the specific missing shape/dtype information can be made accessible to an early LCNF compiler pass through explicit type declarations*, with a clearly bounded implementation cost and clearly stated restrictions.
